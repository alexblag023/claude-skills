# Профили внешних SAST принимающей стороны

Приёмка ПО часто идёт по отчёту **внешнего** сканера. Эксперт SAST должен знать, как такой сканер «видит» код, чтобы не ставить `PASS` там, где он поставит High (см. `scanners_and_tooling.md` §9). Статусы: **[ФАКТ]** — подтверждено открытым источником (ссылка), **[ГИПОТЕЗА]** — вывод по косвенным данным. Содержание пересказано, правила вендора закрыты: точные сигнатуры неизвестны.

## Профиль: Solar appScreener (ранее Solar inCode)

Разработчик — «Ростелеком-Солар». Определён по отчёту: в нём указаны «appScreener», версия продукта и правил 3.16.2, генератор PDF — JasperReports.

### Из руководства пользователя 3.13.1 (прочитано целиком, 172 с.) [ФАКТ]
- **Руководство не содержит перечня классов уязвимостей и сигнатур** (слова «CSRF» там нет): классификации подключаются через CWE 4.0, CWE/SANS Top 25 (2011 и 2021), OWASP Top 10 (2017 и 2021), OWASP Mobile Top 10, MASVS, PCI DSS 4.0, HIPAA и БДУ ФСТЭК. Список правил проверить по руководству нельзя; полноту покрытия оцениваем эмпирически (`coverage_matrix.md`).
- **Какие файлы разбирает анализатор HTML5:** `.aspx .cshtml .js .jsf .jsm .jsp .jspx .htm .html .phtml .php .ts .vbhtml .vue .xht .xhtml`. Файлов `.jinja .j2 .jinja2 .tmpl .twig .ejs .hbs .erb .svelte` в списке **нет** — такие шаблоны этим сканером не анализируются (наш линтер проверяет их строже, это запас, а не расхождение). Python — только `.py`; конфигурации — `.config .xml .properties .policy .aspx .ini .plist`.
- **Правила HTML5 — XPath по дереву разметки:** узлы `htmlElement`, `htmlAttribute`, `htmlAttributeName`, `htmlAttributeValue`; пример пользовательского шаблона ищет атрибут с заданным значением. Это подтверждает: правило CSRF по формам — сигнатура разметки, серверная логика ему не видна.
- **Режим скана:** при инкрементальном анализе сканируются только изменённые или новые файлы; по умолчанию полный (`incremental=false`). Для ряда языков (включая HTML5, JavaScript, PHP) инкрементальный режим указан отдельно.
- **Fuzzy Logic Engine** включается режимами (в т.ч. пользовательским) с порогами по уровням критичности; отчёт может показывать значение FLE и скрывать «отклонённые» и «подтверждённые» разделы по настройкам экспорта — часть находок в выгрузке может отсутствовать.
- **Статусы** находок: Не обработано / Подтверждено / Отклонено; отклонённые не входят в рейтинг и подсчёт; подтверждённые динамическим анализом помечаются отдельно.
- **Пользовательские правила:** XML-паттерны (XPath), на языках от JavaScript и TypeScript до Python, Perl, PL/SQL, Ruby, T-SQL, C/C++, HTML5; обязательны название, уровень критичности и confidence.

### Выводы для аудита [ГИПОТЕЗА, по косвенным данным]
- Находка CSRF в шаблонах HTML5 — это **сигнатурное правило по разметке**: `<form method=post>` без поля токена в самой форме. Серверный Origin-/Sec-Fetch-гвард и токен, подставляемый middleware, в шаблоне не видны, поэтому не засчитываются. Основание: отчёт с 8 такими находками при рабочем гварде; алгоритм вендора закрыт.
- Классификаторы привязаны к редакции OWASP/CWE релиза (в описании CSRF — OWASP Top 10 2013 A8): не ждите учёта современных фреймворковых защит.
- Критерий «High/Critical» вендор определяет по своей шкале: 4 уровня, рейтинг 0–5 по числу Critical/High на объём кода.
- Статус «Подтверждено» ставит человек на стороне принимающей: отклонить находку можно только его решением, а не аргументом в нашем отчёте.

### Что делать до сдачи
1. Прогнать `scripts/csrf_template_lint.py` по всем шаблонам и JS — это самый дешёвый способ воспроизвести классический High (CSRF).
2. Запросить у принимающей стороны **полный** отчёт (Critical…Low), а не только High; формат CSV удобнее PDF: его читает DefectDojo (открытый), см. `scanners_and_tooling.md`.
3. Уточнить версию правил, набор классификаторов, режим скана (полный/инкрементальный) и применённые фильтры экспорта.
4. Каждую находку внешнего скана закрывать правкой исходника с видимым следом защиты; спорную — только через оформленное отклонение (`security exception`, `MANUAL`).
5. После правки перегнать внешний скан: заявленный фикс считается подтверждённым только по его выводу.

### Ограничения знаний
Сигнатуры правил, набор правил по Python/JS/HTML и алгоритм Fuzzy Logic закрыты вендором. Не заявляйте «мы воспроизводим appScreener»: линтеры скилла — это модель наиболее типичных срабатываний, а не эмулятор. Руководство пользователя вендора ([PDF 3.13.1](https://rt-solar.ru/products/solar_appscreener/files/doc/rukovodstvo-polzovatelya-appscreener.pdf), >10 МБ) содержит полный список классов и настроек — читать при необходимости полной сверки.

## Как добавлять профили других сканеров
Для каждого внешнего сканера принимающей стороны (SonarQube, Checkmarx, Fortify, PT AI, Svace и др.) заведите раздел с теми же полями: что за продукт и версия, метод (паттерны/taint/AST), классификаторы, форматы выгрузки, режим скана, **как он реагирует на «невидимые» защиты**, чек-лист подготовки. Только проверяемые факты со ссылками; домыслы помечайте `[ГИПОТЕЗА]`.
