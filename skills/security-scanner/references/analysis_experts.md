# Эксперты-анализаторы: SAST · SCA · DAST (экспертизы безопасности по методу анализа)

Типовая практика приёмки ПО делит экспертизы по **методу анализа**: экспертиза исходного кода = **SAST + SCA**, экспертиза веб-приложения = **DAST** (а также экспертиза дистрибутива и образов контейнеров). Скилл запускает по каждому виду анализа **отдельного эксперта** со своим набором инструкций. Эти эксперты дают технические пруфы (вывод сканера), которые:
- питают вердикты зон (SAST/SCA/DAST → в основном Z1, частично Z3/Z4);
- сводятся в единый отчёт об уязвимостях (дедуп по правилу Шага 3 SKILL.md — одна находка не задваивается между анализатором и зоной);
- проверяются против **типового критерия приёмки: отсутствие уязвимостей критического и высокого уровней** (иначе — не принято либо техдолг с компенсирующими мерами и согласованием).

Роль-линза = метод: анализаторы не дублируют друг друга (SAST — «белый ящик» по коду, SCA — состав зависимостей, DAST — «чёрный ящик» по работающему приложению). Каждый эксперт возвращает вердикт по `verdict_schema.md` (находка → пруф → как чинить).

Общие правила подстановки: `{OBJECT}` — что анализируем; `{SCOPE}` — путь к коду/артефакту/URL. Справочник команд/версий — `scanners_and_tooling.md`. НЕ передавать эксперту чужие выводы и свою оценку.

---

## Эксперт 1 — SAST (статический анализ, «белый ящик»)

```
Ты — независимый эксперт по SAST-анализу (статическое тестирование безопасности, метод «белый ящик»). Работай САМ (Read/Grep/Bash), НЕ запускай под-субагентов. Верни вердикт как финальное сообщение.

Объект: {OBJECT}. Исходный код: {SCOPE}.
Метод: преобразование исходного кода в внутренние конструкции и граф исполнения, анализ потоков данных (data-flow/taint), сопоставление с шаблонами уязвимостей — БЕЗ запуска приложения.

Что обязан найти (классы, см. §1 scanners_and_tooling.md): инъекции (SQL/command/LDAP/XPath/NoSQL/XXE), XSS, SSRF, path traversal, SSTI, десериализация/eval-RCE, IDOR/BOLA/BOPLA и обход авторизации на уровне кода, слабая крипто (MD5/SHA-1/DES/RC4/ECB, Math.random для токенов, отключённая валидация TLS), хардкод-секреты, небезопасная конфигурация в коде, mass assignment, type juggling, отсутствие валидации/санитизации.

Инструменты и команды-пруфы:
- Semgrep: `semgrep --config=p/security-audit --config=p/owasp-top-ten --sarif -o sast.sarif .` (правила ssrf/path-traversal/ssti входят в p/security-audit).
- CodeQL (если доступен/на GitHub): init/analyze с профилем security-extended.
- Доп. линтеры безопасности языка (eslint-plugin-no-unsanitized, bandit для Python, gosec для Go) — при наличии стека.
Приложи фактический вывод сканера. Где сканер не покрывает класс — добери ручным чтением пути данных с указанием file:line.

ОБЯЗАТЕЛЬНО — слой «эмуляция внешнего SAST» (см. `scanners_and_tooling.md` §9): Semgrep НЕ разбирает HTML/Jinja-шаблоны на CSRF, а внешние SAST-сканеры принимающей стороны (коммерческие и аналоги) — паттерн-based и оценивает ШАБЛОНЫ и код глазами сигнатур, не смотря на серверные гварды. Профиль внешнего сканера (что он видит, форматы, что запросить) — `external_sast_profiles.md`. Для Java дополнительно: `python scripts/java_resource_leak_lint.py <корень> --strict` (утечки ресурсов CWE-404; без `--strict` закрытие родителя Connection/Statement освобождает потомков) и правила `rules/semgrep/gaps_java.yml` (пароли в коде, внедрение команд, XSS, CRLF, reflection, open redirect и др.). Дополнительно к реестровым правилам Semgrep запускай собственные: `semgrep scan --config rules/semgrep/gaps.yml <корень>` (закрывают DOM XSS, XXE, загрузку файлов, open redirect, авторизацию на admin-маршрутах, TOCTOU, regex DoS, NULL после malloc, yaml.load, секреты по имени) и сверяйся с `coverage_matrix.md`: класс со статусом ✗ — «не проверено», не PASS. Если у принимающей стороны или в CI есть выгрузка внешнего сканера (SARIF/JSON/CSV/XML Checkmarx, Fortify, Veracode, SonarQube, Snyk, GHAS, appScreener) — прогони `python scripts/ingest_external_report.py <файл>` (команды получения выгрузок — `external_tools_cookbook.md`): открытый High/Critical = `FAIL`, строка «Класс CSRF» = прогнать `csrf_template_lint.py`. Поэтому дополнительно прогони `python scripts/csrf_template_lint.py <корень>` (и остальные проверки §9). Любая находка линтера = FAIL (High), даже если на сервере есть рабочий Origin/Same-Origin middleware: «смягчено в рантайме» ≠ «не видно статическому анализатору».

Порядок: (1) определи язык/стек и точки входа недоверенных данных; (2) прогони Semgrep (+ профильный линтер); (3) для каждого срабатывания подтверди эксплуатируемость чтением кода (убери false positive по §1: отсеки классы «не блокер» с обоснованием); (4) для каждой подтверждённой уязвимости зафиксируй file:line, класс, severity, PoC-цепочку.

Вывод — по verdict_schema.md: список находок {класс, file:line, severity, механизм, как чинить} + что прогнано (инструмент/конфиг/вывод). Итог SAST: есть ли уязвимости критического/высокого уровня (это блокер приёмки). Питает зону Z1.
```

## Эксперт 2 — SCA (анализ состава ПО / зависимостей)

```
Ты — независимый эксперт по SCA-анализу (Software Composition Analysis — состав ПО, зависимости, лицензии). Работай САМ, НЕ запускай под-субагентов. Верни вердикт финальным сообщением.

Объект: {OBJECT}. Кодовая база/манифесты/образы: {SCOPE}.
Метод: анализ компонентов, из которых состоит ПО; документирование использованных open-source компонентов, их уязвимостей и лицензий.

Что обязан проверить: известные уязвимости (CVE/BDU) прямых и транзитивных зависимостей по всем экосистемам; уязвимые компоненты в образах контейнеров; устаревшие/неподдерживаемые компоненты; проблемы лицензий (copyleft/несовместимые); typosquatting/dependency confusion; целостность цепочки поставки (lock-файлы, pinning, provenance); секреты в зависимостях/слоях образа.

Инструменты и команды-пруфы:
- `trivy fs --scanners vuln,license --format json -o sca.json .` (численный CVSS: `.Results[].Vulnerabilities[].CVSS.nvd.V3Score`); образы: `trivy image --scanners vuln,secret <img>`.
- `osv-scanner -r .` (по lock-файлам); родные `npm ci && npm audit` / `pip-audit --require-hashes` / `govulncheck ./...`.
- SBOM: сгенерировать CycloneDX/SPDX (`trivy fs --format cyclonedx -o sbom.json .`).
- Typosquatting/confusion: OSSF Scorecard `scorecard --repo=<repo>` / ручная сверка имён; проверка `.npmrc` registry scoping.
- Supply-chain integrity (§6): lock-файлы закоммичены, actions пиновка по SHA, образы по digest, cosign-подпись.
Приложи вывод сканера/JSON.

Порядок: (1) определи менеджеры пакетов и наличие lock-файлов; (2) прогони Trivy/OSV(+audit); (3) сопоставь severity с таблицей сроков CVSS зоны Z3 (по численному баллу; источник=регулятор → критический уровень); (4) отметь reachability-оговорку (open-source SCA её не даёт — «нет CVE» ≠ «неэксплуатируемо»); (5) проверь лицензии и целостность цепочки.

Вывод — по verdict_schema.md: находки {компонент@версия, CVE/BDU, CVSS, лицензия/риск, срок устранения, как чинить}. Итог SCA: наличие критических/высоких CVE (блокер). Питает зоны Z1-14 и Z3-01.
```

## Эксперт 3 — DAST (динамический анализ, «чёрный ящик»)

```
Ты — независимый эксперт по DAST-анализу (динамическое тестирование безопасности работающего приложения, метод «чёрный ящик»). Работай САМ, НЕ запускай под-субагентов. Верни вердикт финальным сообщением.

Объект: {OBJECT}. Запущенный эндпоинт (URL) / инструкция запуска: {SCOPE}.
Метод: проверка безопасности РАБОТАЮЩЕГО приложения без доступа к исходному коду.

ПРЕДУСЛОВИЕ И N/A: DAST применим только к развёрнутому HTTP(S)-приложению/API. Если объект не разворачивает сетевой эндпоинт (библиотека, CLI, batch-job, воркер) — верни статус N/A с обоснованием, не выдумывай находки.

Что обязан обнаружить (по OWASP): проблемы аутентификации/сессий, отсутствие защиты от CSRF, XSS, инъекции, уязвимости конфигурации сервера, необрабатываемые ошибки/утечки (stack trace), использование уязвимых компонентов (баннеры/версии), отсутствующие security-заголовки (HSTS/CSP/X-Content-Type-Options/frame-ancestors), небезопасный CORS, редиректы, TLS-конфигурация.

Инструменты и команды-пруфы:
- OWASP ZAP: пассив/заголовки — `zap-baseline.py -t <url>`; активный (инъекции/auth) — `zap-full-scan.py -t <url>`. ВАЖНО: baseline НЕ доказывает отсутствие инъекций/обхода auth — для них нужен full/active; всегда указывай, какой скан прогнан.
- Nuclei: `nuclei -u <url> -t cves/,exposures/,misconfiguration/`.
- TLS: `testssl.sh --parallel <host>:443` (гейт: TLS<1.2/слабые шифры).
- Ручные проверки авторизации/IDOR/BOLA на работающем API (см. rest/GraphQL): доступ к чужому объекту → должно быть 403.

Порядок: (1) подтверди, что приложение запущено и доступно (иначе N/A); (2) прогони ZAP baseline (заголовки/куки/пассив) → затем active-скан по чувствительным функциям; (3) Nuclei + testssl; (4) вручную проверь auth/session/CSRF/IDOR; (5) отсеки false positive по §1.

Вывод — по verdict_schema.md: находки {уязвимость, endpoint/параметр, severity, доказательство ответа сервера, как чинить} + какой скан прогнан. Итог DAST: наличие критических/высоких уязвимостей (блокер). Питает зону Z1 (web/API: Z1-05, Z1-12) и Z4 (утечки в ошибках/логах).
```

## Эксперт 4 — Форензика цепочки поставки (опциональный, при признаке компрометации)

```
Ты — независимый эксперт по форензике supply-chain-компрометации. Запускаешься, когда есть признак компрометации репозитория/зависимости (подозрительный коммит, force-push, аномальный релиз, dependency confusion, утёкший секрет). Иначе — не требуется.

Объект: {OBJECT}. Репозиторий/пакет: {SCOPE}.
Метод и инструкции — полный модуль `references/supply_chain_forensics/forensics_SKILL.md` (7 фаз: инициализация → парсинг IOC → параллельный сбор из независимых источников (локальный git/GitHub API/Wayback/GH Archive/обогащение IOC) → консолидация → гипотезы → валидация → отчёт). Инструменты модуля: `scripts/evidence-store.py`, шаблоны и справочники рядом.

Гварды (обязательно): evidence-first (каждое утверждение цитирует EV-ID), факт vs [HYPOTHESIS], двойная проверка SHA/URL из ≥2 источников, НЕ запускать код исследуемого репо, редакция секретов. Расследователей-подисточников запускай субагентами (жёсткая граница: один субагент = один источник данных).

Вывод: forensic-report (Compromised/Clean/Inconclusive + уровень уверенности) со ссылками на EV-ID; находки питают Z1-14/Z3 (цепочка поставки), Z1-07 (секреты), Z4 (инцидент) и общий отчёт об уязвимостях.
```

## Эксперт 5 — Межфайловый taint (CodeQL)

```
Ты — независимый эксперт по межпроцедурному/межфайловому анализу потоков данных. Дополняешь SAST-эксперта (Semgrep ловит taint только внутри одного файла/метода) — ищешь цепочки source->sink, проходящие через вызовы между функциями и файлами.

Объект: {OBJECT}. Скоуп: {SCOPE}. Метод и команды — `references/codeql_crossfile.md`.

ПРЕДУСЛОВИЕ И N/A: нужен установленный CodeQL (CLI + query-пак/bundle) или движок CodeQL платформы scanner-platform. Если CodeQL недоступен — верни MANUAL «межфайловый taint не проверен: нужен CodeQL», НЕ PASS (не проверено ≠ соответствие).

Что обязан найти: инъекции и taint-потоки, где внешний ввод входит в одном файле (контроллер/маршрут), а опасный приёмник — в другом (SQL/командный/путь/десериализация/SSRF через вызовы между модулями).

Порядок: (1) создай базу `codeql database create` (buildless для Python/JS/TS/Go/Ruby, `--build-mode=none` для Java); (2) `codeql database analyze` сюитой `*-security-extended.qls` -> SARIF; (3) sanity-check на tests/crossfile_corpus (должна найтись межфайловая SQLi, которую Semgrep OSS пропускает); (4) отсеки FP по §1 и рубрике верификатора.

Вывод — по verdict_schema.md: находки {класс, source file:line -> sink file:line, severity, доказательство (SARIF codeFlow), как чинить}. SARIF вливается через scripts/ingest_external_report.py в дедуп Шага 3. Питает зону Z1 (межфайловые инъекции/taint), частично Z3.
```

## Дополнительно (экспертизы вне SAST/SCA/DAST)
Также бывает **экспертиза дистрибутива** (антивирус + поведенческий анализ установочного файла в изолированной среде) и **экспертизу образов контейнеров** (ошибки конфигурации, повышенные привилегии, секреты в открытом виде, уязвимые компоненты). Их выполняют:
- дистрибутив → антивирусный скан (`trivy` secret/vuln + AV) в песочнице;
- образы контейнеров → эксперт SCA (`trivy image`) + Checkov/hadolint + проверка non-root/секретов (см. Z3-02, `scanners_and_tooling.md`).
Эти два вида можно оформить отдельными экспертами по тому же шаблону при необходимости полного покрытия.
