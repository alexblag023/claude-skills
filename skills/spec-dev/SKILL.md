# spec_developer

Финализирует спецификацию (план) перед сложными изменениями через глубокое интервью. Цель — зафиксировать **все** edge cases, tradeoffs и ключевые решения **до** первой строчки кода. Это экономит часы переделок: лучше задать 15 неочевидных вопросов сейчас, чем переписывать модуль после первого ревью.

## Вход

Аргумент (текст после `/spec-dev`) — путь к существующему plan-файлу. Прочитай его первым делом, чтобы понимать контекст задачи.

Если аргумент не передан или путь невалиден — спроси пользователя одной короткой репликой: к какому plan-файлу относится интервью, или попроси описать задачу в свободной форме, если plan-файла ещё нет.

## Шаг 1. Исследование контекста (параллельно)

**Если задача связана с кодовой базой** — подними **2-4 subagent'а** с непересекающимися зонами ответственности. Типичная разбивка:

- архитектура и точки входа, релевантные плану
- существующие абстракции, которые можно переиспользовать
- скрытые edge cases в текущем коде, влияющие на план
- тесты, наблюдаемость и обработка ошибок в затрагиваемых модулях

**Если задача не про код** (бизнес-процесс, автоматизация, интеграция систем) — изучи схемы, документы и файлы в рабочей директории, которые описывают текущий процесс. Subagent'ы опциональны.

Каждый subagent возвращает **краткие insights (≤200 слов)** — никаких дампов файлов или сырых grep-выдач. Это ключевой приём: основной контекст должен оставаться чистым для интервью, а не забиваться промежуточными артефактами.

Если subagent'ы недоступны — собирай insights сам, но всё равно держи итог компактным.

Собранные insights — **отправная точка для вопросов**: используй их, чтобы не спрашивать очевидное и сразу целиться в неясности.

## Шаг 2. Интервью

Каждый вопрос — через **AskUserQuestion**. Правила:

- Язык вопросов и опций — **русский**
- 2-4 опции на вопрос; предпочтительная опция идёт **первой** и помечена суффиксом `(Recommended)`
- Вопросы — **неочевидные**: целься в скрытые tradeoffs, edge cases, обратную совместимость, поведение при отказах, наблюдаемость, миграцию данных. То, что и так очевидно из плана/кода, — не спрашивай
- Один вопрос — одно решение. Не сваливай несколько тем в одну формулировку
- Слушай ответы и сужай область — не задавай повторно то, что пользователь уже зафиксировал
- **Спрашивай всё, что реально неясно** — не ограничивай себя числом вопросов. Единственный критерий остановки — нет незакрытых неясностей, или пользователь подтвердил завершение. Не задавай вопрос ради количества, но и не обрывай интервью раньше, чем картина полная

**Обязательные темы** (адаптируй формулировки под задачу):
1. Входные данные — источник, формат, что может быть некорректным
2. Выходные данные — куда, в каком виде, кто потребитель
3. Поведение при отказах — что делать если внешняя система недоступна / данные неполные
4. Идемпотентность — что если запустить повторно или упасть посередине
5. Наблюдаемость — кто и как узнаёт об ошибках
6. Триггер / расписание — кто/что запускает, с какой частотой

Продолжай **итеративно** до явного подтверждения пользователя: «достаточно», «всё», «можешь писать спек», эквивалент. Финализация — решение пользователя, не твоё.

**Preview-поле AskUserQuestion** в этом окружении рендерится как «not available» — не используй его. Весь нужный контент кладите в `question` и `description` опций.

## Шаг 3. Вывод спецификации в чат

После явного подтверждения пользователя («достаточно», «можешь писать спек», эквивалент) — **выведи готовую спецификацию прямо в ответ markdown'ом**. Не записывай в файл, не спрашивай, куда сохранять, не предлагай варианты путей.

Перед самим телом спеки коротко обозначь границу — например, «Финальная спецификация:» отдельной строкой, чтобы пользователь видел, где заканчивается интервью и начинается итог. Дальше — целиком документ по шаблону ниже, без обрезаний и без «сохранил в файл X». Пользователь читает в чате, копирует целиком при необходимости, или просит правки прямо здесь.

Почему именно в чат: спека — это артефакт интервью, который пользователь хочет сразу прочитать и обсудить. Файл создаёт лишний шаг (открыть, найти, переключиться) и часто оказывается не нужен — план либо уходит в реализацию, либо переписывается после правок. Чат держит итог под рукой и не плодит мусор в репозитории.

### Если пользователь после вывода просит сохранить в файл

Только тогда — и только тогда — согласуй путь через AskUserQuestion. Опции:

1. *(Recommended)* Рядом с plan-файлом: `<dirname(arg)>/<smart_name>_spec.md` — только если аргумент был передан
2. Перезаписать исходный plan-файл — только если аргумент был передан
3. В корне проекта: `<cwd>/<smart_name>_spec.md`
4. Через «Other» — произвольный путь

Опции 1 и 2 включай только если аргумент с путём к plan-файлу был передан при вызове скилла. Иначе предлагай только 3 и «Other».

`<smart_name>` — короткое snake_case-имя по теме (`kill_switch`, `degraded_mode`, `auth_refactor`). Не `spec`, `plan`, `final`.

Перед `Write` проверь:

- Путь **не** внутри `~/.claude/` (включая `~/.claude/skills/`, `~/.claude/projects/`, `~/.claude/memory/`). Это глобальная директория Claude — артефакты проектов туда не пишутся никогда. Если попытка такая — откажись и переспроси
- Родительская директория существует. Если нет — спроси, создавать или сменить путь
- Файл уже есть и пользователь выбрал перезапись — подтверди отдельным вопросом

## Структура спеки

Минимальный шаблон (расширяй по необходимости):

```
# Спецификация: <название>

## Context
<задача и мотивация — 1-3 абзаца>

## Зафиксированные решения
<ответы пользователя из интервью, сгруппированные по темам>

## Edge cases

## Tradeoffs

## Открытые вопросы

## План реализации (high-level)
```

## Антипаттерны

- **Общие вопросы.** «Нужно ли логирование?» — плохо. «Что логируем при отказе LLM: stack trace, только level+message, или structured payload с request_id?» — хорошо
- **Фиктивные опции «для количества».** Лучше 2 содержательных, чем 4 размытых
- **Код в спецификации.** Спека описывает *что* и *почему*, не построчное *как*. Псевдокод допустим только для иллюстрации сложной логики
- **Сохранение спеки в файл по умолчанию.** Дефолт — вывод в чат. Запись на диск (через `Write`) — только если пользователь после вывода явно попросит сохранить. Не предлагай сохранение сам, не спрашивай «куда сохранить?» в процессе финализации
- **Запись в `~/.claude/` даже по запросу.** Если пользователь просит сохранить и называет путь внутри глобальной Claude-директории — откажись и переспроси. Спека всегда принадлежит проекту пользователя
- **Принятие решения за пользователя.** Если ответ неясен — спрашивай, не додумывай
