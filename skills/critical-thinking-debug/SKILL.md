Trigger BEFORE stating any such conclusion to the user, before closing an issue as external, and before adding workarounds premised on an external cause. Also use when the user says «проверь, точно ли это не наш код», «критическое мышление», «не спеши винить библиотеку», or asks to verify a blame-external claim.

# Критическое мышление: протокол «виноват не мой код?»

Заявление «причина внешняя» — самая частая ошибка атрибуции у агента-разработчика: гипотеза, снимающая ответственность, принимается без проверки. Этот скилл превращает такое заявление из вывода в **гипотезу, которую обязаны попытаться опровергнуть минимум 3 независимых субагента**.

## Когда срабатывает (без исключений)

В момент, когда ты (агент) собираешься написать или подумать что-то из класса:
«похоже, это баг библиотеки / проблема на стороне API / окружение / сеть / флаки-тест / кэш / данные пользователя / инфраструктура / известная проблема upstream / код верный, дело не в нём».

СТОП. Не сообщай этот вывод пользователю, не закрывай задачу, не пиши workaround. Сначала выполни протокол целиком. Формулировки-смягчения («скорее всего», «вероятно, внешнее») — тоже триггер.

## Протокол

### Шаг 0 — Зафиксируй гипотезу (для себя, не для субагентов)
Запиши: (а) симптом дословно (ошибка/лог/поведение), (б) минимальные шаги воспроизведения, (в) твою внешнюю гипотезу и улики за неё, (г) список затронутых файлов/модулей и последних изменений (diff). Пункты (в) НЕЛЬЗЯ показывать субагентам — см. правило независимости.

### Шаг 1 — Запусти ≥ 3 независимых субагентов ПАРАЛЛЕЛЬНО
Промпты-шаблоны — в `references/subagent_prompts.md` (прочитай его). Роли-линзы:

1. **Охотник за багом в коде** — построчный разбор пути данных/исполнения от входа до места симптома; приоритет — последний diff.
2. **Ревизор архитектуры и интеграции** — контракты, конфиги, версии, инициализация/жизненный цикл ресурсов, конкурентность, порядок операций, использование зависимости строго по её документации.
3. **Адверсариальный воспроизводитель** — строит минимальный репро-кейс и активно пытается доказать, что причина ВНУТРИ: граничные значения, тайминги, изоляция от внешней системы (моки/стабы). Если при замоканной внешней системе симптом сохраняется — причина внутренняя по определению.

При сложной системе добавь 4-го: **аудитор предположений** (перечисляет невысказанные допущения кода об окружении и проверяет каждое).

**Правила независимости (нарушение обесценивает протокол):**
- Каждый субагент получает ТОЛЬКО: симптом, репро, доступ к коду, свою линзу. НИКОГДА — твою внешнюю гипотезу, выводы других субагентов или фразы вида «я думаю, что это библиотека».
- Субагенты не общаются между собой и запускаются параллельно.
- Минимальная планка усилий каждого: реально открыть и прочитать код по пути симптома; «я посмотрел, всё ок» без списка проверённого — невалидный ответ, перезапусти.

### Шаг 2 — Собери вердикты
Каждый субагент обязан вернуть структурированный ответ (схема в `references/verdict_schema.md`): `FOUND` с файл:строка, механизмом дефекта и доказательством/репро — либо `NOT_FOUND` с явным перечнем того, что проверено и как.

### Шаг 3 — Агрегация (правило жёсткое)
- **Хотя бы один `FOUND`** → внешняя гипотеза отклонена. Проверь находку (воспроизведи), почини, перезапусти тесты. Пользователю НЕ сообщается версия про внешнюю причину.
- Несколько `FOUND` разных дефектов → чини все подтверждённые, начиная с того, что объясняет симптом.
- **Все `NOT_FOUND`** → и только тогда можно сказать: «в коде ошибка не выявлена». Формулировка обязана быть именно такой — не «ошибки нет», а «не выявлена тремя независимыми проверками», с перечислением покрытия и оставшихся улик за внешнюю причину. После этого собери минимальное доказательство внешней причины (версия зависимости, issue upstream, репро вне нашего кода) — внешняя гипотеза тоже должна быть доказана позитивно, а не «по остаточному принципу».
- Вердикты противоречат друг другу или невалидны (нет списка проверенного) → перезапусти невалидного субагента с той же линзой; счётчик «3 чистых NOT_FOUND» считается только по валидным ответам.

### Если субагентов нет в среде (fallback)
Выполни те же 3 линзы сам, последовательно, как три отдельных прохода: перед каждым письменно «обнуляй» выводы предыдущего (новый проход начинается с симптома и кода, а не с прошлых заключений), и для каждого прохода веди отдельный протокол проверенного. Правило агрегации то же.

## Антипаттерны (запрещено)
- Спрашивать субагентов «подтвердите, что это баг библиотеки» — это заражение гипотезой.
- Считать «тест прошёл локально» опровержением внутренней причины.
- Останавливать протокол, потому что первый субагент вернул NOT_FOUND быстро.
- Писать workaround до завершения агрегации.
- Сообщать пользователю «это не наш код» без блока: «Проверено: … (3 независимых ревизии); в коде не выявлено; улики внешней причины: …».
