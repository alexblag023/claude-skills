# Голосование, агрегация и итоговое решение

Оправочный документ. Все формулы реализованы в `scripts/aggregate_votes.py`: скрипт считает
по этим правилам, а не «на глаз». Оркестратор может переопределить вердикт, но обязан
записать это в `override` и объяснить в отчете.

## 1. Что и чем измеряется

| Величина | Что это | Откуда |
|---|---|---|
| `R` | рубрика: качество решения по 5 критериям (0..4) | ревью Critics |
| `R_w` | рубрика, взвешенная по надёжности ревьюера | ревью + история вердиктов |
| `P` | pairwise-ранжирование (Copeland) | парные сравнения в обеих позициях |
| `S` | итоговая оценка: `0.7*R_w + 0.3*P` | вычисляется скриптом |
| `hard_gate` | проверка исполнением: compile + lint + тестовые AC | VERIFY |
| `hidden_ratio` | доля пройденных скрытых тестов | VERIFY |

## 2. Рубрика

Пять критериев, шкала 0..4:

| Критерий | 0 | 2 | 4 |
|---|---|---|---|
| `correctness` | неверно | работает частично | верно во всех случаях |
| `ac_coverage` | закрыт 0 критериев | закрыта половина | закрыты все |
| `robustness` | падает на границах | терпит крайние случаи | терпит и сообщает об ошибке |
| `simplicity` | избыточно сложно | приемлемо | минимально |
| `spec_adherence` | нарушает спеку | частично | полностью |

Веса по умолчанию: `correctness` 0.40, `ac_coverage` 0.25, `robustness` 0.15, `simplicity` 0.10,
`spec_adherence` 0.10. Веса переопределяются в `config.rubric_weights` и попадают в хэш
конфигурации.

**Агрегация оценок по ревьюерам:**

- 2 ревью на кандидата -> среднее арифметическое;
- 3 и больше -> медиана (среднее арифметическое завышает оценку при расхождении).

Отсутствующий критерий считается нулём и порождает предупреждение: пропуск — не «не важно»,
а отсутствие данных.

## 3. Взвешивание по надёжности

`w_rel(j) = (pass_j + 1) / (n_j + 2)` — сглаживание Лапласа по истории вердиктов ревьюера.
Для новой модели `w_rel = 0.5`: ни одна модель не получает решающий вес из воздуха.

Итоговый вес ревьюера: `w_j = w_role(j) * w_rel(j)`, где `w_role`: critic 1.0, judge/escalation
1.2.

**Ограничение:** отношение `w_max / w_min` не должно превышать 2 — иначе одна модель
становится диктатором. Скрипт ограничивает веса и пишет предупреждение.

`R_w(c) = Σ_j w_j · R_j(c) / Σ_j w_j` — взвешенное среднее по **индивидуальным** оценкам
ревьюеров (не по агрегированным).

## 4. Pairwise и Copeland

Каждая пара кандидатов предъявляется ревьюеру **в двух порядках**. Вердикт, меняющийся при
перестановке, засчитывается как ничья (борьба с позиционным bias). Голос агента в паре с
собственным кандидатом исключается.

`P(c) = (wins(c) - losses(c)) / pairs(c)`, затем линейная нормализация в 0..1:
`(raw + 1) / 2`. Если пар нет — `P = 0.5` (нейтрально, без наказания за отсутствие данных).

## 5. Итоговая оценка и ранжирование

`S(c) = 0.7 · R_w(c) + 0.3 · P(c)`.

Ранжирование **лексикографическое**, порядок ключей важен:

1. `hard_gate` — прошел ли проверку исполнением (True раньше False);
2. `hidden_ratio` — доля пройденных скрытых тестов;
3. `S`;
4. `cid` — для полной воспроизводимости сортировки (алфавитный, детерминированный).

**Исполнение важнее голосов.** Кандидат с лучшим `S`, но упавший на тестах, не может
победить кандидата, который тесты прошел. Расхождение записывается в `dissent` с пометкой
`votes_vs_execution`.

## 6. Предфильтр

Кандидат исключается из подсчета, если:

1. **Критический дефект подтвержден двумя независимыми ревьюерами.** Отпечаток дефекта:
   `sha1(ac + severity + нормализованное место)`, номера строк нормализуются, чтобы
   находки разных ревьюеров про один дефект совпали. **Независимость = разные семейства:**
   два ревьюера одного семейства не считаются независимым подтверждением.
2. **Один ревьюер нашёл критический дефект, и проверка исполнением упала.** Соответствие
   ищется по `ac` дефекта (упавшая проверка `ac:<id>`); фолбэк «любая непройденная проверка»
   применяется только если у дефекта нет `ac`.

**Одиночный неподтвержденный critical — это не исключение, а флаг для REPAIR.** Иначе один
резкий ревьюер вычеркивает сильный кандидат.

## 7. Кворум

Требуется `N // 2 + 1` голосов в поддержку победителя:

- N=3 -> 2 из 3;
- N=4 -> 3 из 4.

**Ревьюер поддерживает кандидата**, если: нет критических дефектов, `correctness >= 3`, и
кандидат не проиграл ни одной паре этого ревьюера. Пара с `consistent = false` (вердикт
меняется при смене порядка) считается **ничьей** и не отнимает голос поддержки. Пара,
у которой обратный порядок не спросили (`consistent` отсутствует), **не засчитывается
вовсе**: ни победа, ни поражение, ничья. Это проверяет код (`scripts/aggregate_votes.py`),
а не добросовестность оркестратора. При N=4 возможен раскол 2:2 — это **не** большинство:
включается эскалация, а не «победил первый».

**Кворум считается от числа участников**, а не от числа выживших кандидатов: исключение
кандидата не должно ослаблять кворум. Число участников берется из `config.n_authors` (или из
ростера), и только при его отсутствии — из числа кандидатов.

## 8. Эскалация и цепочка разрешения ничьей

**Цепочка tie-break (по порядку, пока не сработало):**

1. **Исполняемая проверка** — если она есть, спор решается ею, а не голосами.
2. **Анонимизированный rubric-scoring** всеми участниками с рандомизированным порядком и
   инверсией для контроля позиционного bias.
3. **Эскалация** к более сильной модели как арбитру (задача — «выбрать и обосновать»,
   а не «решить заново»).

Если арбитр недоступен (например, платная модель — только по личному указанию владельца),
дефолт — лучший rubric-score с пометкой `escalation_unavailable`, и окончательное решение
остается за владельцем.


При ничьей (`|S_1 - S_2| < delta_tie`, `delta_tie` по умолчанию 0.05, и одинаковый
`hidden_ratio`) запускается Judge:

- Judge — модель, **не являвшаяся** автором ни одного из двух кандидатов, и не их критиком.
- Задача Judge: выбрать один, опираясь на спеку, AC и конкретные дефекты ревью.
- Ответ Judge — **дополнительный голос с весом 1.2**, а не замена голосования.
- Если Judge тоже не определился — `NO_CONSENSUS` с явным указанием двух кандидатов.

## 9. Вердикты

| Вердикт | Когда |
|---|---|
| `ACCEPT` | кворум набран, победитель прошел `hard_gate`, нет разногласий и неподтвержденных критических дефектов |
| `ACCEPT_WITH_NOTES` | то же, но есть расхождение ревьюеров (разброс `correctness` >= 2) или одиночный неподтвержденный critical |
| `NO_CONSENSUS` | кворум не набран или ничья, которую не разрешил Judge |
| `REJECT_ALL` | ни один кандидат не прошел `hard_gate` |
| `DEGRADED` | участников меньше двух, либо часть штурма не выполнена (все кандидаты упали в REPAIR) |

Окончательный вердикт принимает **Chair** на основании агрегации и может смягчить
`NO_CONSENSUS` до `ACCEPT_WITH_NOTES` или `DEGRADED` с явным указанием причины.
Он **не может** повысить `REJECT_ALL` до `ACCEPT` — это право владельца, и оно фиксируется
в `override`.

## 10. Решение — не сводка

Итоговое решение должно быть **исполнено** по правилам ниже, а не выбрано само.

### Порядок

1. Три кандидата переводятся в **структурированный вид**: словарь с типами -> поле ->
   структура -> обоснование -> компромисс.
2. **Внешняя оценка** (Judge) сопоставляет кандидатов по AC и дефектам ревью.
3. Если внешней оценки нет (задача не исполняема) — решение считается гипотезой:
   указывается, что подтверждает её и что опровергнет.
4. **Синтез** выбирает:
   - элемент A из кандидата 1, элемент B из кандидата 2, элемент C из кандидата 3 —
     **если** каждый элемент совместим с AC и не конфликтует с остальными;
   - иначе — один кандидат целиком.
5. Синтезированное решение **прогоняется через VERIFY**. Если оно хуже победителя по
   тестам — откат к победителю.

### Почему не «взять лучший ответ»

- Победитель по голосам может быть хуже победителя по исполнению (см. §5).
- Отдельный элемент может быть объективно лучше соответствующего элемента победителя.
- Синтез без проверки исполнением — гипотеза, а не решение.

### Когда синтез запрещен

- Элементы конфликтуют (несовместимые схемы, разные модели данных, разные протоколы).
- Источник каждого элемента не установлен.
- Синтез нарушает критерий приемки.

В этих случаях берут победителя целиком и записывают, почему синтез не состоялся.

## 11. Что фиксируется в артефакте

Помимо чисел подсчета, в `run.json` пишутся:

- `decision_rule` — какой метод сработал (`quorum`, `tie_break_execution`, `tie_break_rubric`,
  `escalation`);
- `vote_counts` — счет по кандидатам;
- `tie_break_path` — пройденные ступени цепочки;
- `escalated` — был ли арбитр и кто;
- `verification_result` — итог исполнения;
- `dissent` — позиция меньшинства, не стертая итогом.

## 12. Метрика успеха методики

Штурм оправдан, если он **лучше одиночного исполнителя на той же задаче**:

- по числу пройденных скрытых тестов;
- по числу найденных критических дефектов (истинных, а не ложных);
- по времени до первого зеленого результата.

Сравнение обязательно: одиночный исполнитель делает ту же задачу в тех же условиях. Без
сравнения утверждение «штурм лучше» не имеет опоры.
