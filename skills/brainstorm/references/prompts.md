# Шаблоны промптов

Все шаблоны — для внешних моделей. Оркестратор (Chair) не отвечает за задачу: он подставляет
свои данные в поля `{...}` и запускает вызовы.

## Общие требования к любому вызову

- Ответ — **только JSON** по схеме, без пояснений и без markdown-обертки.
- Числа — без единиц измерения и без локализованных разделителей.
- Если чего-то не хватает — значение `null` или пустой список, а не выдумка.
- Схема ответа проверяется скриптом `scripts/validate_answers.py`; при ошибке формата — один
  повтор с требованием «верни только JSON по схеме».

## 0. Префаза: роль автора

```
Ты решаешь одну задачу. Другие модели решают ее независимо и не увидят твой ответ.

ЗАДАЧА
{spec}

КРИТЕРИИ ПРИЕМКИ
{acceptance}

ПУБЛИЧНЫЕ ПРИМЕРЫ
{examples}

ПРАВИЛА
- Дай одно цельное решение. Не перечисляй альтернативы.
- Если в задаче есть выбор архитектуры, выбери один вариант и обоснуй его.
- Явно перечисли предположения, которые не следуют из текста задачи.
- Перечисли самопроверки, которые ты можешь выполнить локально.
- Укажи риски и то, что может сломаться.
- Уверенность (confidence) — от 0 до 1. Не завышай: если решение содержит непроверяемое
  допущение, честно снизь оценку.

ФОРМАТ ОТВЕТА (строго этот JSON, без других полей):
{
  "solution": "текст решения",
  "assumptions": ["..."],
  "self_tests": ["..."],
  "risks": ["..."],
  "confidence": 0.0
}
```

## 1. Ревью (Critic)

```
Ты ревьюишь чужое решение. Автор неизвестен и не будет тебе раскрыт.

ЗАДАЧА
{spec}

КРИТЕРИИ ПРИЕМКИ
{acceptance}

РЕШЕНИЕ {cid}
{candidate}

ЧТО СДЕЛАТЬ
1. Проверь каждый критерий приемки и поставь pass | fail | unknown.
2. Найди дефекты. Не выдумывай: на каждый дефект укажи место, утверждение и доказательство
   (строка, фрагмент, сценарий). Дефект без доказательства не считается дефектом.
3. Оцени решение по рубрике: correctness, ac_coverage, robustness, simplicity, spec_adherence,
   каждая от 0 до 4.
4. Если даны два кандидата, сравни их: укажи победителя и решающий довод.

ЧТО НЕ ДЕЛАТЬ
- Не переписывать решение. Ты ревьюер, а не второй автор.
- Не ставить pass по умолчанию.
- Не указывать дефект, которого нет в тексте.

ФОРМАТ ОТВЕТА (строго этот JSON):
{
  "cid": "{cid}",
  "ac_results": {"AC-1": "pass"},
  "defects": [
    {"severity": "critical|major|minor", "ac": "AC-1",
     "location": "file.py:12", "claim": "...", "evidence": "..."}
  ],
  "rubric": {"correctness": 0, "ac_coverage": 0, "robustness": 0,
            "simplicity": 0, "spec_adherence": 0},
  "pairwise": [{"a": "C1", "b": "C2", "winner": "C1", "consistent": true}]
}
```

> `pairwise` заполняется только если даны два кандидата. Если дан один — массив пустой.
> Значение `winner` — метка кандидата: `a` или `b` соответственно.
> Поле `consistent` заполняет НЕ модель, а оркестратор: после того как та же пара
> предъявлена в обратном порядке, он ставит false, если вердикт изменился (тогда
> пара считается ничьей). Пока обратный порядок не проверен, поле не заполняется —
> и такая пара **не засчитывается вовсе** (см. `scripts/aggregate_votes.py`).
>
> **Если показаны два кандидата, рубрика и дефекты относятся к каждому отдельно.**
> Общая рубрика на двоих недопустима: приписать одну оценку двум решениям — значит
> выдумать оценку. Тогда формат ответа другой:
>
> {
>   "reviews": [
>     {"cid": "C1", "ac_results": {"AC-1": "pass"}, "defects": [], "rubric": {...}},
>     {"cid": "C2", "ac_results": {"AC-1": "fail"}, "defects": [], "rubric": {...}}
>   ],
>   "pairwise": [{"a": "C1", "b": "C2", "winner": "C1", "reason": "..."}]
> }
>
> Приводить ответ к виду, который считает агрегатор, — работа скрипта
> `scripts/normalize_reviews.py`: он разбирает ответ по кандидатам, **отвергает**
> неоднозначную общую рубрику и сам ставит `consistent`, сравнивая вердикт с ответом
> на ту же пару в обратном порядке. Оркестратор эту проверку не выполняет руками:
> согласованность пары должна обеспечиваться кодом.

## 2. Pairwise-сравнение (отдельный вызов, оба порядка)

```
Выбери лучшее из двух решений для одной задачи. Отвечай только по критериям и фактам.

ЗАДАЧА
{spec}

КРИТЕРИИ ПРИЕМКИ
{acceptance}

РЕШЕНИЕ X
{candidate_x}

РЕШЕНИЕ Y
{candidate_y}

Дай победителя и один решающий довод, и риск проигравшего.

ФОРМАТ ОТВЕТА (строго этот JSON):
{
  "winner": "X|Y|tie",
  "decisive_reason": "...",
  "risk_of_loser": "..."
}
```

**Вызов дважды** с переставленными X и Y (это 2N вызовов на парные сравнения плюс N
вызовов на ревью рубрикой). Если вердикты разошлись — пара считается ничьей, и поле
`consistent` в ревью ставится в `false`.

## 3. Эскалация (Judge)

```
Два кандидата не разошлись голосами. Ты разрешаешь спор по фактам.

ЗАДАЧА
{spec}

КРИТЕРИИ ПРИЕМКИ
{acceptance}

КАНДИДАТ {cid_a}
{candidate_a}

КАНДИДАТ {cid_b}
{candidate_b}

НАХОДКИ РЕВЬЮ
{review_findings}

Выбери один кандидат. Если оба равноценны — так и скажи: tie.

ФОРМАТ ОТВЕТА (строго этот JSON):
{
  "winner": "{cid_a}|{cid_b}|tie",
  "decisive_reason": "...",
  "risk_of_loser": "..."
}
```

## 4. Починка (REPAIR)

```
Исправь указанные проблемы в своем решении. Не переписывай решение целиком.

ЗАДАЧА
{spec}

ТВОЕ ТЕКУЩЕЕ РЕШЕНИЕ
{candidate}

ПРОВАЛИВШИЕ ПРОВЕРКИ
{failing_checks}

НАХОДКИ РЕВЬЮ
{review_findings}

ПРАВИЛА
- Изменяй только то, что нужно для устранения указанных проблем.
- Не трогай то, что работает.
- Не добавляй функциональность сверх задачи.
- Если починка требует неразрешимого компромисса — не чини, а объясни в ответе.

ФОРМАТ ОТВЕТА — unified diff (только изменяемые строки):
--- a/{file}
+++ b/{file}
@@ -старт,число +старт,число @@
 контекст
-удаляемая строка
+добавляемая строка
```

> В починку передаются **только имена упавших проверок и сообщения assert** (не более 2000
> символов), **без исходников скрытых тестов**: иначе решения начнут подстраиваться под тесты
> вместо исправления дефекта.

## 5. Синтез (SYNTHESIZER, опционально)

```
Собери итоговое решение из лучших элементов нескольких кандидатов.

ЗАДАЧА
{spec}

КРИТЕРИИ ПРИЕМКИ
{acceptance}

КАНДИДАТЫ (с пометкой источника каждого элемента)
{candidates_with_provenance}

НАХОДКИ РЕВЬЮ
{review_findings}

ПРАВИЛА
- Каждый элемент итогового решения должен иметь источник (C1, C2, C3).
- Не бери элемент, нарушающий критерий приемки.
- Если элементы конфликтуют — оставь целиком один кандидат и объясни, почему синтез не
  состоялся.
- Не добавляй ничего, чего нет в кандидатах.

ФОРМАТ ОТВЕТА: сначала краткое решение (до 300 слов), затем unified diff.
```

## 6. Ответ внешнего ревьюера (Judge для неисполняемых задач)

Когда задачу нельзя проверить исполнением, внешняя оценка становится голосом, а не фильтром.
Ее результат попадает в `reviews[]` с `role: judge` и весом 1.2 — так же, как ревью
критиков, но **не** может отменить провал исполнения.

```
Оцени решение относительно критериев приемки и верни вердикт по рубрике.
...
ФОРМАТ ОТВЕТА (строго этот JSON):
{
  "cid": "{cid}",
  "ac_results": {"AC-1": "pass"},
  "defects": [],
  "rubric": {"correctness": 0, "ac_coverage": 0, "robustness": 0,
            "simplicity": 0, "spec_adherence": 0}
}
```

## 7. Разведка (Recon)

Шаблон для агента разведки. Агент получает **только свою зону** и вопрос — без выводов
других агентов и без гипотез автора. Он **не пишет решение**: его работа — факты с
доказательствами и честные пробелы знания.

```
Ты — агент разведки. Твоя зона: {zone}.

ЗАДАЧА
{question}

ТВОЯ ЗОНА (пути)
{scope}

ЧТО СДЕЛАТЬ
1. Собери факты по своей зоне: точки входа, контракты, границы, состояние, риски.
2. Каждый факт подтверди чтением кода: укажи файл и строку.
3. Запиши и то, что НЕ удалось проверить, — пробел знания важен: решение не должно
   опираться на догадку.
4. Решение не предлагай — это работа участников штурма.

ФОРМАТ ОТВЕТА (строго этот JSON, без других полей):
{
  "facts": [
    {"location": "путь/файл.py:строка", "claim": "что там фактически есть",
     "evidence": "как это проверено: что прочитано или запущено"}
  ],
  "unknowns": ["что не удалось проверить и почему"],
  "risks": ["риски, найденные в своей зоне"]
}
```

> **Почему так.** Разведка отвечает на вопрос «как устроено», а не «что делать». Если
> агент разведки предлагает решение, он перестаёт быть независимым наблюдателем и
> подменяет участников штурма — а именно они должны соревноваться.


## Системные дополнения к промпту

- **Фаза DIVERGE:** добавь «Другие модели решают эту задачу независимо; их ответов ты не увидишь.
  Не пытайся угадать их решения и не оставляй в ответе оговорки вида «возможно, другой подход
  лучше».
- **Фаза CROSS-CHECK:** добавь «Ты ревьюишь чужую работу. Твоя задача — найти дефекты, а не
  предложить свое решение».
- **Всегда:** «Считай каждое утверждение о коде или API, которое ты не проверил, за
  непроверенное и перечисли их в `assumptions` или `risks`.
